ROOT CAUSE (confirmed by gcc -E, not inferred)
----------------------------------------------
get_rel_type_and_sym() is the ONLY consumer (modpost.c:1372-1373):

    *r_type = ELF_R_TYPE(r_info);
    *r_sym  = ELF_R_SYM(r_info);

gcc -E expansion of the two headers differs in exactly those two lines:

  CURRENT (fixed)                     BIONIC-BUG repro
  ----------------------------------  --------------------------------
  *r_type = ((unsigned long long)(r_info) & 0xffffffffULL);   *r_type = ((r_info) & 0xff);
  *r_sym  = ((unsigned long long)(r_info) >> 32);            *r_sym  = ((r_info) >> 8);

Ground truth from init/main.o .rela.text entry 0 (EM_AARCH64, entsize 24):
    r_info  = 0x000000b400000113
    correct r_sym  = r_info >> 32 = 0xb4   = 180
    correct r_type = r_info & 0xffffffff = 0x113 = 275 (R_AARCH64_ADR_PREL_PG_HI21)
    buggy   r_sym  = r_info >> 8  = 0xb4000001 = 3019898881   <-- gdb shows exactly this
    buggy   r_type = r_info & 0xff = 0x13 = 19

init/main.o has 485 symbols, so index 3019898881 is structurally impossible.
tsym = symtab_start(0x7ffff7d4b7a8) + 3019898881*24 = 0x8010d7d4b7c0, which is
non-canonical on x86-64 -> the load faults immediately.

The faulting instruction (section_rela+175) shows the 24-byte Elf64_Sym
stride being used to index with the bogus r_sym; the stride itself is correct,
only the index is wrong.

WHY THE OLD REPORT AND THE NEW BEHAVIOUR DISAGREE
------------------------------------------------
The pre-fix modpost.h (4212680b^) does NOT itself define ELF64_R_SYM. It only
aliases `ELF_R_SYM -> ELF64_R_SYM` (line 51) and relies on the host <elf.h>.
On this glibc host that yields the CORRECT (i)>>32, so a build of the pre-fix
header also does not crash here (verified: modpost_PREFIX exits 1, not 139).
The crash requires a host whose <elf.h> supplies the 32-bit encoding, i.e. a
Bionic/Android host — which is exactly what the fix commit's message says the
shim was for. Hence: reproducible on the original Bionic host, NOT reproducible
on this Linux codespace with the same header.

THIS ALSO EXPLAINS THE 'file size changed' RED HERRING
-----------------------------------------------------
No mmap write is involved. The .o is opened PROT_READ|PROT_WRITE MAP_PRIVATE by
parse_elf() and modpost only reads from it. init/version.o's observed size
change (148280 -> 148088) is the KERNEL BUILD still running in the background
relinking/regenerating that object while gdb was reading it, not modpost
writing to its mapping. MAP_PRIVATE guarantees none of modpost's writes would
persist to the file in any case. The float-OBServa experiment was chasing a
moving target, not a memory-corruption signal.
